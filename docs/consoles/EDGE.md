## Plan (18:50 UTC)
- **What deploys.** `WebXR/dist/` is the flat build: the homepage, 13 app bundles (1–5.6 MB single HTML files),
  `tracks/`, `shared/*.js`, lazy `sims/`, `vendor/` (fonts, icons), `media/`, `models/`, `og/`, `icons/`,
  `auth-config.json`, sitemap/robots/manifest/404. Nothing is hash-named, so nothing can honestly be `immutable`
  except the folders whose contents change only with a pinned version or a re-encode (`vendor/`, `media/`, `models/`,
  `og/`, `icons/`, `tracks/img/`). Navigational HTML is `no-store`; the bundles revalidate (`max-age=0,
  must-revalidate` — Pages answers a 304 on the ETag, which is what a returning visitor wants after a rebuild).
- **One Pages project, Functions for `/api/*`.** Root `wrangler.toml` is the Pages project (`pages_build_output_dir =
  "WebXR/dist"`, a KV binding `CF_ENTERPRISE`). `functions/api/[[path]].js` and `functions/auth-config.json.js`
  re-export the router in `workers/edge/router.mjs`; `WebXR/dist/_routes.json` (emitted by the bundler) sends only
  `/api/*` and `/auth-config.json` to the Function so every other request is a plain static hit. The same router also
  has a `default.fetch`, and `workers/edge/wrangler.toml` publishes it as a standalone Worker on a zone route for a
  deployment that wants `/api/*` on its own Worker (optional, `CF_WORKER_ZONE`).
- **Routes.** `GET /api/health`; `GET /api/auth-config` (and `/auth-config.json` itself, so the pages' own same-origin
  read picks the injection up without any change to `auth.js`): the static file, with the organisation's `enterprise`
  block from KV (`org:<host>` then `org:<?org=>` then `org:default`) merged over the file's, whitelisted keys only,
  `no-store`; `POST /api/payments/webhook` → TILL's `workers/payments/handler.mjs` (default `handle(request, env)`,
  named `ROUTES`; stubbed here because TILL builds in parallel — the stub is marked, take TILL's on the add/add
  conflict).
- **Security headers** (`_headers`, generated by `tools/bundle_webxr.py` from the hosts the code names): CSP allowing
  `cdnjs.cloudflare.com` (three, react, mapbox-gl), `cdn.jsdelivr.net` (msal), `accounts.google.com` (GSI),
  `api.mapbox.com`/`events.mapbox.com`, `login.microsoftonline.com`; `connect-src` also `https:` because the
  deployment-configured endpoints (guide, email, LRS, LTI) are whatever the operator names in `auth-config.json`.
  No `frame-ancestors`/`X-Frame-Options` — the LTI launch embeds these pages. `'unsafe-inline'` is unavoidable: each
  bundle is one HTML file with its modules inline.
- **`_redirects`**: the repo-layout paths (`/<app>/`, `/<app>/index.html`, `/<app>/dist/<page>`, `/home.html`,
  `/portal/*`) → the flat names, generated from `DIST_PAGES`.
- **Deploy agent** `tools/deploy_agent.mjs`: build → gate → provision → deploy → configure → verify → rollback, dry run
  by default (prints every command and check, exits 0), `--apply` only with `CLOUDFLARE_API_TOKEN` and
  `CLOUDFLARE_ACCOUNT_ID` in the environment; secrets by name only; every step appends to `docs/deploy/last-run.md`
  (`--log` moves it, the checker logs to scratch). `tools/deploy_cloudflare.sh` is the thin shell front (prints the
  commands). Workflow `.github/workflows/deploy-cloudflare.yml`: the checker suite, then the agent with `--apply` on
  the default branch, gated on the secrets being present.
- **Checker** `tools/check_deploy.mjs` in `check_all`: configs parse; every `_headers` path exists in `dist`; no secret
  or account id (32-hex, `pk./sk.`, `CLOUDFLARE_API_TOKEN=` values) anywhere in the deploy files or the log; the
  router's routes ⊇ TILL's `ROUTES`; the plan is complete, ordered and runs nothing without credentials; the verify
  step's assertions are the listed ones; `wrangler` dry run when installed (it is not here — skipped with a note).
