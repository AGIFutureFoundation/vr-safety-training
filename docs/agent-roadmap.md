# Agent roadmap — Foreman, the platform agent

A staged plan to run a platform agent, working name **Foreman**, that answers learners, recommends the next station, supervises a robot running a station in simulation, and can later be registered on agent protocols. The draft definition is `agents/foreman/agent.json`; `tools/check_agent.mjs` (in `tools/check_all.mjs`) keeps it honest.

> **Read this first.** The Virtuals Protocol sites and documentation (virtuals.io) **could not be reached from this build environment**. Everything below about Virtuals Protocol, SingularityNET or any other protocol is written from this repository's existing adapter (`WebXR/shared/agent-protocols.js`) and general public knowledge only. **Every protocol detail must be verified against the current official documentation before any integration.** This page deliberately states no version numbers, endpoints, contract or wallet addresses, chain ids, token figures or fees; where one of those is needed, it comes from the provider's own current documentation at deploy time, never from this page.

## 1. Capabilities as functions

Foreman's capabilities are functions over three things the repository already has. Each function in `agents/foreman/agent.json` has JSON-schema parameters and a `binding` to a real module export; the checker fails the build if a binding, a primitive or an example station does not resolve.

| Function | What it does | Binds to |
| --- | --- | --- |
| `describe_station` | a station's task graph, preconditions, failure labels, programmes, union | `WebXR/shared/skill-registry.js` `skStation` |
| `plan_station` | the ordered primitive plan with parameters | `skStation` |
| `check_preconditions` | PPE / lockout in force at a step | `skPreconditionsAt` |
| `run_station_in_sim` | run a robot through a station on the real engine | `WebXR/shared/robot.js` `runEpisode`, `robot-embodiment.js` `runEmbodiedEpisode` |
| `recommend_next_station` | the first station in a programme the passport does not show as passed | `WebXR/shared/passport.js` `ppProgramme`, `skStationsForProgramme` |
| `learner_progress` | a learner's own programme progress | `ppProgramme` |
| `answer_learner` | an answer grounded in the station content and docs | `skStation` (retrieval over the Guide's knowledge base is milestone M1) |
| `export_dataset` | local native / LeRobot-style / RLDS-style exports | `tools/lib/dataset_formats.mjs` `createFormatWriters` |

**The skill registry** (`WebXR/shared/skill-registry.js`, generated by `tools/gen_skill_registry.mjs`) is the vocabulary: every step kind as a robot primitive — select → reach-and-press, sequence → ordered-reach-and-press, find → search-and-press, gauge → hold-in-band, hold → press-and-hold, track → track-a-signal, turn → rotate-to-angle, drag → pick-and-place, drive → path-follow — and every station (633) as a task graph of those primitives with preconditions (PPE, lockout, from a documented keyword rule) and failure labels (its hazards and its interruptions). **The passport** is the learner's own record, on their device. **The Guide's knowledge base** is the station content (each step's cue and reason, each hazard's explanation) and `docs/`.

## 2. Simulation harness

The agent never drives a real robot from this platform. It drives `WebXR/shared/robot.js` through a station in simulation, and it is scored by the same engine (`WebXR/shared/game.js`) that scores a learner: the same stars, the same unsafe-action count, the same keep-out account when embodied (`robot-embodiment.js`), the same `noRobot` hand-off to a person.

- **Plan** with `plan_station`; **gate** each step with `check_preconditions` (a supervisor refuses a lockout-gated step whose lockout step has not completed).
- **Run** with `run_station_in_sim`, deterministic for a seed, headlessly through `tools/lib/headless.mjs` — the path `tools/robot_train.mjs` and `tools/export_dataset.mjs` already use.
- **Score** from the engine's summary only. The agent's own opinion of how it did is never the score.
- **Learn** from the exports: `node tools/export_dataset.mjs` writes native shards plus `lerobot/` and `rlds/`; `node tools/robot_train.mjs --from-lerobot <dir>/lerobot` trains the per-primitive baseline and reports success per primitive; `node tools/eval_dataset.mjs <dir>` validates both layouts.

## 3. Virtuals Protocol

*Written from general public knowledge and `agent-protocols.js`; unverified here. Verify every detail against the current official documentation before any integration.*

**The G.A.M.E framework**, as generally described, defines an agent by a **goal** and a **description**, and gives it **workers**, each owning a set of **functions** with typed parameters that the agent's planner may call; SDKs are published for Python and TypeScript. `agents/foreman/agent.json` follows that shape: a goal, a description, three workers (`learner-guide`, `sim-supervisor`, `data-steward`) and eight functions with JSON-schema parameters. It is a **draft shape**, not a configuration for any SDK: field names, the planner's contract, how functions return results and how state is held must all be checked against the current SDK documentation, and an adapter written against it, before anything runs.

**The Agent Commerce Protocol**, as generally described, lets agents offer, accept and deliver jobs to one another. The repository's `virtuals` adapter speaks only a generic job-offer / deliverable shape — `offer(bundle)`, `deliver(bundle, consent)`, `status(receipt)` — and starts with every field unset (`endpoint`, `chainId`, `agentRegistryAddress`, `paymentTokenAddress`). Until a deployment fills them from the provider's current documentation, `offer()` and `deliver()` refuse with "configure per the provider's current documentation", before touching the network.

**Mapping.** Foreman's functions that could be offered as jobs are the ones with no personal data in or out: `describe_station`, `plan_station`, `check_preconditions`, `run_station_in_sim` (a seeded simulation result) and `export_dataset` over **synthetic rollouts only**. `learner_progress`, `recommend_next_station` and `answer_learner` read the learner's passport and stay on the device; they are never offered to another agent. Any job, payment or fee terms are the deployment's to set from the provider's own documentation; this page states none.

## 4. SingularityNET and the other adapters

The same rule applies to every adapter in `agent-protocols.js`; each is a generic shape, unconfigured, refusing until configured from the provider's current documentation.

- **`singularitynet`** — a service-descriptor style offer with a payment-channel placeholder (`endpoint`, `organizationId`, `serviceId`, `paymentChannelAddress`). As generally described, services on that marketplace are published by an organisation and called through a daemon with a payment channel. Foreman's simulation and planning functions map onto a service's methods the same way they map onto jobs above. Verify the service-definition format and the payment mechanism against the current official documentation first.
- **`generic-attestation`** — an attestation payload with a schema-id placeholder, for any attestation registry a deployment configures. The only thing Foreman would ever attest is a **digest** that a learner chose to share (see §5), never the record itself.
- **`cloudflare-relay`** — the relay template in `integrations/cloudflare/`; still only a configured endpoint from this side.

## 5. Wallets, consent, data licensing — and what never goes on-chain

- **Consent is unchanged.** Nothing leaves the learner's device without their opt-in (`WebXR/shared/share-engagement.js`, `wallet.js`); an adapter's `deliver()` refuses without a consent record. Exports are local files.
- **On-device by default.** Training records, episodes and the passport live in the browser's storage. The agent reads them there.
- **Wallets.** `wallet.js` stays as it is: no key is generated, held or logged by this platform's agent. A deployment that needs a wallet uses the learner's own, with its own consent screen.
- **Data licensing.** Synthetic rollouts are CC0-1.0. Human episodes carry no asserted licence: whoever distributes them must hold the learner's or hall's permission. Every exported episode says so in its `licence` and `consent` fields.
- **Never on-chain, and never sent to an agent protocol:** personal data of any kind, names, crew tags (even hashed), training records, episodes, pose tracks, passport contents, or anything from which a learner could be re-identified. At most, a learner-chosen digest or attestation reference.
- **Not a certification.** Passing a station in simulation, for a robot or a learner, is evidence of a procedure under this engine's scoring, not a credential.

## 6. Milestones

Each milestone has acceptance tests; a milestone is done when its tests are in `tools/check_all.mjs` and pass.

- **M0 — Registry, exports, draft agent (this change).** Accept: `tools/gen_skill_registry.mjs --check` is current; LeRobot-style and RLDS-style layouts validate (`tools/check_dataset_tools.mjs`, `tools/check_agent.mjs`); `robot_train.mjs --from-lerobot` reports a success rate per primitive; every function in `agent.json` binds to a real export; no key, secret, address, URL or network call.
- **M1 — Answer and recommend, offline.** Accept: `answer_learner` retrieves from station content and `docs/` with a citation to the station and step; `recommend_next_station` returns the first unpassed station of a programme from a fixture passport; nothing leaves the device (a checker asserts no network call in the agent's code path).
- **M2 — Simulation harness.** Accept: the agent runs `plan_station` → `check_preconditions` → `run_station_in_sim` headlessly for every station in one programme; engine scores are reproducible for a seed; a lockout-gated step attempted before its lockout is refused; `noRobot` steps are handed off, never attempted.
- **M3 — Supervised robot policy.** Accept: a policy trained on the exports beats the per-primitive baseline's held-out agreement on every primitive with data, with zero keep-out violations on the embodied suite.
- **M4 — Protocol dry run.** Accept: with every adapter unconfigured, each protocol path refuses with the documented sentence and sends nothing; a mock endpoint (local, in the checker) receives only synthetic, consented bundles; no personal data appears in any payload.
- **M5 — Verified integration (gated on review).** Accept: each protocol's details are verified against its current official documentation and recorded with the date checked; a named reviewer signs off; configuration lives only in deployment settings, never in the repository; the M4 tests still pass against the configured adapter's payloads.
